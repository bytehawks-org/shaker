# From Bitnami scripts to Shaker

This is the review that motivated Shaker: what the Bitnami container scripts did to configure,
normalize and standardize an installation, what stays valuable, what is replaced, and how to port
an application. (Bitnami names are quoted from the public `bitnami/containers` layout - verify
against the version you migrate from; Shaker does not depend on them.)

## What Bitnami did

Per application, a set of hand-written bash scripts under `/opt/bitnami/scripts/<app>/` sharing a
common library set:

| Layer | Bitnami | Role |
|---|---|---|
| env | `<app>-env.sh` | read `<APP>_*` variables (and `*_FILE`), compute defaults and derived paths |
| build | `postunpack.sh` | at image build: users, directories, permissions (`g+rwX`, gid 0), symlinks, config massaging |
| init | `setup.sh` (+ `lib<app>.sh`) | at start: validate input, render config, initialize data, run init scripts (`/docker-entrypoint-initdb.d`), persist |
| entry | `entrypoint.sh`, `run.sh` | print banner, call setup, `exec` the service as uid 1001 |
| libs | `liblog libos libfs libfile libvalidations libnet libservice libpersistence libversion libwebserver ...` | reusable primitives |
| tools | `render-template`, `wait-for-port`, `gosu` | small binaries |
| layout | `/opt/bitnami/<app>`, data in `/bitnami/<app>`, uid 1001 gid 0, `BITNAMI_DEBUG` | conventions |
| legacy | stacks / `ctlscript.sh`, `/opt/bitnami/apps`, `bnconfig` | the VM / server flavour |

Strengths worth keeping: one convention for all apps; env-var driven configuration with `*_FILE`
secrets; OpenShift-compatible permission model; idempotent start; init-script directories; debug flag.

Weaknesses Shaker addresses:

| Weakness | Consequence | Shaker |
|---|---|---|
| imperative script **per application** | every app re-implements validation, rendering, persistence; drift between apps | generic engine + declarative bundle |
| no parameter schema | no types, no docs, no uniform errors, no discoverability | Rosetta map: types, defaults, required, `--help-vars` |
| env only | legacy hosts need files; two code paths | same resolver reads files, drop-ins, env, CLI |
| no record of what happened | "which build, when initialized, was it edited?" unanswerable | state, events, recipe hash, drift detection |
| config drift invisible | manual edits silently lost or kept | SHA-256 drift check, parameters vs file separation |
| tied to the Bitnami image/ecosystem | cannot be used with distro packages | distro-agnostic, works on any host and any base image |
| one-way (container-centric) | VM/server story was a separate product | same verbs on both |

## Function mapping

| Bitnami (lib) | Shaker | Notes |
|---|---|---|
| `info warn error debug`, `BITNAMI_DEBUG` (liblog) | `log_event`, `log_info`..., `BH_SHAKER_DEBUG`, `BH_SHAKER_LOG_LEVEL` | levels, secret masking, stderr only |
| `is_boolean_yes`, `is_int`, `validate_port`, `is_empty_value` (libvalidations) | `is_boolean_yes`, `is_int`, `is_uint`, `is_port`, `validate_type` | typed, driven by the map |
| `am_i_root`, `ensure_user_exists`, `ensure_group_exists`, `run_as_user`, `generate_random_string` (libos) | same names (`fs.libsh`), + `exec_as_user` | `exec` keeps PID 1 |
| `ensure_dir_exists`, `is_dir_empty`, `configure_permissions_ownership` (libfs) | same names | recursion/mode rules documented |
| `replace_in_file`, `render-template` (libfile) | `replace_in_file` (**literal**, not regex), `render_template` `{{ }}` | no sed -i, no extra binary |
| `wait-for-port`, `get_machine_ip` (libnet) | `wait_for_port`, `is_port_open` | `/dev/tcp`, no nc |
| `is_service_running`, `stop_service_using_pid` (libservice) | `is_service_running`, `service_stop`, `service_start_detached` | + `shaker stop/unit` |
| `persist_app`, `restore_persisted_app` (libpersistence) | `lifecycle_persistence` (`persist\|path\|volume`) | seed + symlink, marker follows data |
| `*_FILE` | Rosetta `ENV_FILE` | any parameter, conflict = error |
| `/docker-entrypoint-initdb.d`, `preinitdb.d` | `first_init` / `pre_init` / `post_init` hook dirs | stage names instead of dirs |
| `<app>-env.sh` | `rosetta.map` | data, generated by Distillery |
| `postunpack.sh` | `shaker install` | data: `user`, `dir` |
| `setup.sh` | `shaker init` | data: `template`, `persist`, `hook` |
| `entrypoint.sh` + `run.sh` | `shaker run` | data: `run`, `stopsignal`, `health` |
| gid 0 + `g+rwX` + nss_wrapper | same model, `ensure_passwd_entry` | OpenShift ready |
| `ctlscript.sh` (VM stacks) | `shaker run --daemon` / `stop` / `unit` | systemd first |
| SBOM per component | `manifest.json` (source URL + sha256, dependency recipe hashes) | SPDX/CycloneDX on the roadmap |

## Variable dialects

Keep your operators' muscle memory: declare the Bitnami name as an **alias** and the canonical name as
the new standard.

```yaml
# distillery packages.yaml
- name: BH_POSTGRESQL_PASSWORD
  type: secret
  required: true
  aliases: [POSTGRESQL_PASSWORD, POSTGRES_PASSWORD]
  file_key: auth.password
  cli: --password
  native_env: PGPASSWORD
```
`docker run -e POSTGRESQL_PASSWORD=... ` and `-e POSTGRESQL_PASSWORD_FILE=...` keep working;
`shaker env pkg --format=explain` shows `alias:POSTGRESQL_PASSWORD`, which is also how you find
deployments still using the old name.

## Porting an application, step by step

1. **Source & build** → Distillery `packages.yaml`: URL template, `sha256`, `depends_on`, `commands`.
2. **`<app>-env.sh`** → `runtime.env`: one entry per variable (type, default, required, aliases = the
   Bitnami names, `file_key`, `cli`, `native_env`). Derived values become template logic or a hook.
3. **`postunpack.sh`** → `runtime.user` and `runtime.dirs` (owner `1001:0`, `g+rwX`).
4. **`setup.sh` config rendering** → files in `distillery/assets/<app>/*.tmpl` and `runtime.templates`.
   `sed` pipelines on the default config become a template with `{{ NAME }}`.
5. **`setup.sh` one-time initialization** (create database, admin user, import seed) → `first_init` hook script.
   Per-start tasks (wait for dependency, migrate) → `pre_init` / `post_init` hooks.
6. **Persistence** (`/bitnami/<app>`) → `runtime.persistence` (`path` in the image → `volume`).
7. **`run.sh`** → `runtime.run.command` as an argv list (no shell), `stop_signal`, `pidfile`.
8. **Health** → `runtime.healthcheck` (`tcp` or `command`) and `runtime.requires`.
9. Build: `autobuilder.py build --package app --with-deps`; test: `shaker install/init/verify/run`.

A worked example is the `nginx` package in Distillery (`packages.yaml`, `assets/nginx/`), built from
source against Distillery's own openssl, zlib and pcre2.

## Behaviour differences to know

* Bitnami images often assume uid 1001 and one app per container; Shaker accepts any uid in group 0.
* `replace_in_file` is literal (Bitnami's is sed/regex): ported scripts that rely on regex need a template instead.
* Bitnami tolerated unknown variables; Shaker rejects unknown CLI flags and conflicting `X`/`X_FILE`.
* Persistence: Bitnami restores config files from the volume on start; Shaker only seeds an empty volume and links - rendering is always from parameters.
* There is no `ALLOW_EMPTY_PASSWORD`-style escape hatch: model it as `required: false` with a default.
